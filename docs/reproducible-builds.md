# Reproducible dependency and SDK resolution

`global.json` selects .NET SDK **10.0.401**, with roll-forward disabled and
prerelease SDKs excluded. Install that exact SDK before restoring. Test, Native
AOT, real-WSLC E2E, and release jobs all install it through setup-dotnet's
`global-json-file` input. Updating the SDK is an explicit reviewed change to this
file, followed by a solution-wide lock refresh and all build checks.

`Directory.Build.props` enables NuGet lock files for all three solution projects.
Commit `src/Wip.Core/packages.lock.json`, `src/Wip.Cli/packages.lock.json`, and
`tests/Wip.Tests/packages.lock.json` together. The Core lock covers its standalone
restore; CLI and test locks also include their project-reference dependency graphs.
Package versions and content hashes are generated by NuGet, not edited manually.
`RuntimeIdentifiers` includes both `win-x64` and `linux-x64` so the same committed
graph covers the Windows shipping target and the Linux test host. It does not
select a single runtime for ordinary managed builds.

`NuGet.Config` clears machine-specific package sources and uses the public NuGet
v3 feed. CI and release jobs first run:

```powershell
dotnet restore wip.slnx --locked-mode
dotnet build wip.slnx --configuration Release --no-restore
dotnet test tests/Wip.Tests/Wip.Tests.csproj --configuration Release --no-build --no-restore
dotnet publish src/Wip.Cli/Wip.Cli.csproj --configuration Release --runtime win-x64 --no-restore --output artifacts/win-x64
```

Locked restore fails if project requests or project-reference dependencies no
longer match the locks. Build, test, and publish do not silently restore a new
graph. The release job uses the same locked restore and Native AOT publish path;
its test step builds the test project with `--no-restore` before publishing.

## Intentional dependency updates and Dependabot

Weekly NuGet Dependabot updates remain enabled at the solution root. Direct
versions stay in `Directory.Packages.props`; review dependency PRs with their lock
changes. Locked mode is a CI command, not an unconditional MSBuild property, so an
updater can regenerate locks deliberately. Do not disable locked mode to make an
incomplete dependency PR pass.

Dependabot can miss downstream project-reference locks with central package
management ([upstream issue 13950](https://github.com/dependabot/dependabot-core/issues/13950)).
If it updates only some locks, check out that PR's feature branch, review the
central version changes, and regenerate **the whole solution** using the pinned SDK:

```powershell
dotnet restore wip.slnx --force-evaluate
git diff -- Directory.Packages.props src/Wip.Core/packages.lock.json src/Wip.Cli/packages.lock.json tests/Wip.Tests/packages.lock.json
dotnet restore wip.slnx --locked-mode
./scripts/Test-LockedRestore.ps1
```

Commit the intended manifest and all resulting lock changes together and run the
normal CI checks. `--force-evaluate` is only for intentional refreshes; it is never
combined with `--locked-mode` in CI. SDK updates can also change SDK-supplied
ILLink/ILCompiler dependencies and therefore require regenerated locks.

## Regression coverage and limits

`scripts/Test-LockedRestore.ps1` runs on both test hosts. In an isolated temporary
solution it verifies the exact SDK, an unchanged locked restore, lock immutability,
rejection of a changed direct dependency request specifically with `NU1004`, and
an intentional whole-solution refresh followed by a successful locked restore.
The checked-out manifests and locks are not modified. Native AOT publish and the
real-WSLC workflow exercise the shipping binary.

This pins SDK selection and NuGet dependency resolution. It does not claim
byte-for-byte binaries across different Windows/Visual C++ toolchain images or
freeze GitHub-hosted runner images. A deliberate release is not required to test
the publish command; do not dispatch the release workflow merely to test it,
because that workflow can tag, attach, and publish release assets.
